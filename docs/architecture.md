# CrossW: архитектура

Статус: согласованная рабочая версия, 2026-09-09.

Что за продукт и по каким правилам пишется контент — в [ТЗ.md](ТЗ.md).
Здесь только устройство кода: слои, правила, форматы, стек.

## 1. Слои

Зависимости идут строго в одну сторону. Обратных нет никогда.

```
  ┌──────────────────────────────────────────────────────────────────┐
  │  src/app/ + src/components/ + src/hooks/     React, DOM, Next     │
  │  Рендерят PlayState, зовут функции движка, ловят события ввода.   │
  │  Игровой логики нет ни строчки.                                   │
  └───────────────────────────────┬──────────────────────────────────┘
                                  │ вызывает чистые функции
                                  ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  src/engine/          Ноль импортов React, DOM и Next             │
  │  PlayState → PlayState. Курсор, ввод буквы, проверка, подсказка,  │
  │  таймер, индекс «клетка → слова». Всё иммутабельно.               │
  └───────────────────────────────┬──────────────────────────────────┘
                                  │ использует типы и разбор
                                  ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  src/core/            Ноль импортов вообще, кроме своих же файлов │
  │  model.ts — типы · grid.ts — разбор сетки и нумерация ·           │
  │  solution.ts — хэш и обфускация · validate.ts — правила контента  │
  └──────────────────────────────────────────────────────────────────┘

  Сборка контента идёт мимо приложения и в рантайме не участвует:

  content/*.json ──▶ tools/build-content.ts ──▶ public/p/<id>.json  (без букв)
   (git, буквы)         (node:fs живёт           public/p/<id>.sol  (решение)
                         только здесь)
```

`node:fs` разрешён только в `tools/`. `core/` и `engine/` не знают ни про
файловую систему, ни про сеть, ни про React — поэтому тестируются вызовом
функции, без jsdom и без моков.

## 2. Три правила

Нарушение любого — повод переписать, а не «поправить потом».

### 2.1. В компонентах нет игровой логики

Компонент делает ровно две вещи: рендерит `PlayState` и зовёт функцию движка в
ответ на событие. Нужно узнать, каким словам принадлежит клетка — спрашивает
индекс, построенный движком один раз при загрузке.

Обоснование не теоретическое. Предыдущий прототип этого проекта нарушал правило
в каждом обработчике и кончил компонентом на 346 строк, в котором проверка ответа
искала слово линейным `.find()` по всем определениям прямо из JSX. Каждая новая
кнопка добавляла ещё один проход по массиву и ещё одну копию правил, которые
через неделю разошлись между собой.

### 2.2. Нумерация вычисляется, а не хранится

Сквозная нумерация — чистая функция от сетки (`core/grid.ts`). В JSON кроссворда
нет ни одного номера, записанного руками.

В прототипе номера лежали в JSON. Результат: существовало два разных слова с
номером 1 — одно по горизонтали, одно по вертикали, — а функция `getCellNumber`
возвращала произвольное из них через `??`. Баг был не в функции, а в том, что
источников правды стало два. Убрали второй — исчез класс ошибок.

### 2.3. Ответы не уезжают в браузер открытым текстом

`content/puzzles/<id>.json` хранит сетку **с настоящими буквами** — так её видно
в git-диффе и можно проверить глазами. На сборке `tools/build-content.ts`
вынимает решение в отдельный файл `public/p/<id>.sol` с XOR-обфускацией по id
кроссворда (`core/solution.ts`), а в `public/p/<id>.json` не остаётся ни одной
буквы ответа.

Честно: **это защита от «посмотреть исходник», а не криптография.** Ключ выведен
из id кроссворда и лежит в том же бандле. Кто откроет devtools и позовёт
`decodeSolution` — получит ответы. И это нормально: игра целиком идёт на клиенте,
сервера нет, спрятать ответы от клиента, который их проверяет, невозможно в
принципе. Цель скромная — чтобы решение не вываливалось случайному любопытному во
вкладке Network одной строкой.

## 3. Дерево файлов

```
docs/                    ТЗ и этот документ — единственная документация
content/                 Исходный контент, ревьюит человек, лежит в git
  topics.json              Темы: id, slug, название, описание, вид (book/film/general)
  packs/<id>.json          Слова темы с определениями и источниками фактов
  puzzles/<id>.json        Кроссворды: сетка с буквами + определения по ключам «1A»/«3D»

  core/                    Ноль зависимостей. Предметная модель и правила
    model.ts                 Типы source- и compiled-форматов. Единственный контракт между слоями

    solution.ts              FNV-1a хэш решения + XOR-кодирование

  engine/                  Чистые функции над иммутабельным состоянием, ноль React
    engine.ts                PlayState и переходы: курсор, ввод, проверка, подсказка
    devPuzzle.ts             Кроссворд-фикстура для тестов и разработки без сборки контента
    engine.test.ts           vitest: движок целиком тестируется вызовами функций
  app/                     Next App Router: страницы, layout, статический экспорт
  components/              Сетка, список определений, панель, шапка. Только рендер
  hooks/                   Мост React ↔ движок: загрузка, localStorage, таймер, клавиатура
  i18n/                    ru.ts — все видимые строки; en.ts добавит английскую версию

  gen.ts                   Генератор сеток из пака и словаря
  build-content.ts         content/ → public/p/: компиляция и вынос решения
  validate.ts              CLI-обёртка над core/validate.ts
```

## 4. Форматы данных

Два формата, не путать. Полное описание типов — в `src/core/model.ts`.

| | source | compiled |
|---|---|---|
| Где | `content/puzzles/<id>.json` | `public/p/<id>.json` + `<id>.sol` |
| Для кого | человек на ревью | плеер в браузере |
| В git | да | нет, собирается |
| Сетка | строки с буквами, `#` — блок | плоский массив чисел: `-1` блок, `0` клетка, `>0` номер |
| Слова | ключи `"1A"`, `"3D"` → текст определения | массив `CompiledEntry` с плоскими индексами клеток |
| Ответы | видны | вынесены в `.sol`, XOR по id |
| Номера | нет вообще | вычислены `core/grid.ts` на сборке |

### Почему `CompiledEntry.cells` — массив плоских индексов

```ts
interface CompiledEntry {
  id: number      // сквозной номер, тот же что в сетке
  dir: Dir        // нужен только для группировки списка на «горизонталь/вертикаль»
  cells: number[] // row * cols + col, по порядку чтения: cells[k] — k-я буква ответа
  clue: string
}
```

Движку не нужно знать ни про геометрию, ни про направление. «Следующая буква» —
это `cells[k + 1]`, а не «строка та же, колонка +1» для горизонтали и наоборот
для вертикали. Вся работа идёт с позицией внутри слова, поэтому у ввода,
проверки и подсказки ровно по одной ветке кода, а не по две.

Второе следствие важнее. Клетка на пересечении — **один и тот же индекс** в
`cells` обоих слов. Буква хранится один раз, по индексу клетки. Значит
расхождение букв между пересекающимися словами невозможно физически: нет двух
мест, которые могли бы разойтись. Сверять пересечения не нужно ни в движке, ни в
валидаторе — сверять нечего.

`dir` остаётся в типе не для логики, а для интерфейса: список определений делится
на «По горизонтали» и «По вертикали».

## 5. Стек и команды

Node 22 · Next.js 15 App Router со статическим экспортом (`output: 'export'`) ·
TypeScript strict + `noUncheckedIndexedAccess` · Tailwind · vitest.

```bash
npm run dev        # разработка
npm test           # vitest: ядро и движок
npm run validate   # проверка контента: паки и кроссворды
npm run content    # content/ → public/p/  (входит в build)
npm run build      # content + статический экспорт в out/
npm run gen        # генератор сеток
```

Сайт статический целиком: ни сервера, ни базы, ни API. `out/` раздаётся откуда
угодно, включая GitHub Pages. Это осознанное ограничение, а не временное
состояние: из него следуют и отсутствие аккаунтов (см. [ТЗ §4](ТЗ.md#4-что-намеренно-не-входит)),
и то, что ответы принципиально на клиенте (см. §2.3).

### Чего сознательно нет

| Не берём | Почему |
|---|---|
| Монорепо с отдельными пакетами | Границы слоёв здесь держатся направлением импортов, а не `package.json`. Три пакета вместо трёх папок дадут ту же чистоту и десять минут установки |
| zod | Единственный вход недоверенных данных — свой же `content/`, и его проверяет `tools/validate.ts` по правилам ТЗ, а не по форме типов. Рантайм-валидация в браузере проверяла бы файл, который сам же и собрал |
| CI | Один разработчик, один рабочий стол. `npm test && npm run validate` перед коммитом делает то же самое без YAML |
| Playwright | Вся игровая логика в `engine/` и покрыта юнит-тестами без DOM. E2E проверял бы, что React рендерит, — а это не то место, где здесь ломается |
| Lighthouse | Статический сайт без картинок и без сторонних скриптов. Мерить нечего |

Общий принцип: при одном разработчике и пяти кроссвордах обвязка стоит дороже
того, что она ловит. Чистота архитектуры здесь стоит ноль строк — она
в направлении зависимостей.
